# Airbnb Supply Opportunity Analysis Constitution

## Core Principles

### I. Essential First and Incremental Delivery
The Essential Level MUST be implemented, verified, documented, and formally closed before work
starts on the Medium Level. The committed project scope includes the complete Essential and Medium
Levels, in that order. Advanced and Expert capabilities MAY be pursued only as extensions after
both committed levels satisfy their quality gates. Optional work MUST NOT delay, replace, or weaken
an Essential deliverable.

Rationale: a complete and trustworthy analytical baseline is more valuable than partially built
advanced features.

### II. Immutable Raw Data and Full Lineage
The six original city CSV files MUST be preserved unchanged in `data/raw/`. Every cleaned,
standardized, joined, filtered, or aggregated dataset MUST be generated by version-controlled code
and written outside the raw layer. The pipeline MUST record source identity, file hash, schema, row
counts, transformation rules, and affected-row counts. Absolute machine-specific paths MUST NOT be
required to reproduce the project.

The sources are public educational data of unknown original provenance and unknown license. Project
documentation MUST state that limitation and MUST NOT describe the datasets as official Airbnb data
or as data supplied directly by Airbnb.

Rationale: immutable inputs and inspectable transformations make every analytical result auditable
and reproducible.

### III. Data Quality Before Analysis
Data profiling and validation MUST precede analytical conclusions. Nulls, duplicates, invalid
values, and outliers MUST NOT be removed, replaced, or winsorized without a column-level rationale,
affected-row counts, and a before/after comparison. Valid extreme observations MUST be retained and
analyzed with robust statistics unless an explicit exclusion rule is approved and documented.

Schema differences between cities MUST remain explicit. Missing source columns MUST be represented
as unavailable values with availability indicators where useful; they MUST NOT be silently replaced
with zero. Listing identity MUST be evaluated at the `city + listing_id` grain unless validation
demonstrates a stronger global key.

Rationale: silent cleaning choices can create stronger bias than the anomalies they attempt to fix.

### IV. Statistical Rigor and Honest Interpretation
Descriptive observations MUST cite reproducible metrics and visual evidence. Every inferential
comparison or hypothesis claim MUST be supported by an appropriate statistical test, correlation,
or confidence interval. Statistical work MUST use an alpha of 0.05, 95% confidence intervals,
effect sizes, assumption checks, and multiple-comparison correction where applicable. A
non-parametric method MUST be used when parametric assumptions are not defensible.

The analysis MUST distinguish statistical significance from practical importance. Correlation MUST
NOT be described as causation. `reviews_per_month` MUST be labeled as a proxy for historical listing
activity, not liquidity, demand, bookings, occupancy, or asset rotation. `price` MUST be described as
a published listing price, not realized revenue, profit, or margin.

Rationale: executive recommendations require evidence whose meaning and uncertainty are explicit.

### V. Notebooks as Auditable Deliverables
The analytical workflow MUST use a short ordered notebook sequence covering data audit and quality,
ETL and cleaning, and executive EDA. Reusable logic MUST live in focused modules under `src/` rather
than being duplicated across notebooks. Every notebook MUST execute from start to finish in a clean,
documented environment without manual state.

Every substantive code section MUST be introduced or explained by Markdown. Each analytical section
MUST end with an explicit conclusion, its supporting evidence, material limitations, and relevance
to the business decision. A notebook that runs but lacks this narrative is incomplete.

Rationale: documentation and reproducibility are evaluated deliverables, not optional polish.

### VI. Decision-First Executive Communication
The project MUST answer: which accommodation types should Airbnb prioritize for host acquisition,
and in which cities and neighborhoods? The central output MUST be a transparent opportunity matrix
at the `city + neighborhood + room_type` grain using relative activity, local price position,
relative supply share, sample size, and dispersion.

The dashboard MUST serve a non-technical executive responsible for supply and host-acquisition
strategy. It MUST favor plain language, a small number of decision-relevant metrics, and traceable
recommendations over visual complexity or opaque composite scores. Any opportunity MUST be described
as provisional because the sources do not include searches, reservations, occupancy, conversion,
revenue, or margin.

Rationale: analysis creates value only when a decision-maker can understand and act on it without
overestimating the evidence.

### VII. Verifiable Git and Kanban Governance
GitHub Projects MUST be the single source of truth for planning. The board MUST use `Backlog`,
`Ready`, `In Progress`, `Review`, and `Done`. Each work item MUST be represented by an issue that
identifies its level, phase, owner, acceptance criteria, and linked pull request.

`main` MUST contain only stable, reviewed work. Changes MUST use short phase-based branches, atomic
descriptive Conventional Commits, and pull requests, including when the project has one contributor.
An issue MUST NOT move to `Done` until its acceptance evidence is present and its pull request is
integrated.

Rationale: traceable delivery prevents undocumented work and keeps status aligned with reality.

### VIII. Comprehensive, Contemporary Documentation
All work MUST be documented as it is performed, not reconstructed only at the end. Documentation
MUST cover decisions, assumptions, source limitations, the data dictionary, transformations,
cleaning rules, code behavior, reproduction commands, statistical results, visualizations,
incidents, rejected alternatives, limitations, and conclusions.

Each material change MUST connect the relevant issue, branch, commits, pull request, validation
evidence, and resulting artifacts. The README and affected technical or analytical documentation
MUST be updated in the same change. A task with stale or missing documentation is incomplete.

Rationale: contemporary documentation preserves the reasoning and evidence required to review,
reproduce, and extend the work.

## Technical and Analytical Constraints

- The required analytical stack is Python, Pandas, NumPy, Matplotlib, Seaborn, Plotly, SciPy,
  statsmodels, and Jupyter. Dependency versions MUST be pinned in version control.
- Power BI Desktop is the required Medium-Level dashboard tool and MUST NOT depend on a paid Power BI
  Service license. The `.pbix` artifact MUST use a documented, portable connection to the generated
  analytical dataset.
- Docker MUST reproduce the Python environment, ETL, automated validations, notebook execution, and
  Power BI-ready analytical dataset. Power BI Desktop and the `.pbix` file run outside the container.
- Technical identifiers and the canonical processed schema MUST use English. Notebooks, conclusions,
  README content, and dashboard labels MUST use Spanish, except for original field names and standard
  technical terms.
- `host_name`, listing `name`, `host_id`, and `listing_id` MAY be retained for raw lineage, duplicate
  checks, and aggregate host-concentration analysis. They MUST NOT appear in public charts, dashboard
  tables, screenshots, README examples, or narrative findings.
- Because source currencies and price reference dates are unknown, price comparisons MUST be made
  only within each city using medians, percentiles, and robust dispersion. Direct monetary rankings
  between cities are prohibited until currency and reference-date metadata are available.
- Because snapshot dates are unknown, the project MUST NOT infer current activity or define
  recency windows from `last_review`. Cross-city recency comparisons are prohibited.
- The minimum statistical analysis MUST test differences in activity by `room_type` within each
  city, test neighborhood differences with a documented minimum sample size and multiplicity
  correction, and assess robust within-city relationships between `minimum_nights`, `price`, and the
  activity proxy.
- A complete EDA MUST include a data dictionary and quality profile, univariate analysis of relevant
  numeric and categorical variables, decision-linked bivariate analysis, segmentation by city,
  neighborhood, and room type, documented outlier analysis, interpretable correlations, and a final
  evidence-and-limitations synthesis.
- The Medium-Level Power BI dashboard MUST contain an executive summary, an acquisition opportunity
  map, and a detail-and-confidence page. Each page MUST answer one clear business question.

## Development Workflow and Quality Gates

Work MUST progress through these phases:

1. Audit and profile the six original sources.
2. Build a reproducible ETL and canonical analytical dataset.
3. Complete the executive EDA and mandatory statistical analyses.
4. Verify and formally close the Essential Level.
5. Build the Power BI dashboard and required advanced visualizations.
6. Verify and formally close the Medium Level.
7. Consider Advanced or Expert extensions only after the committed scope is complete.

Before a task can move to `Done`, its pull request MUST provide evidence for all applicable gates:

- original-file identity and hash checks;
- expected schema checks by city;
- row-count reconciliation before and after transformations;
- exact-duplicate and candidate-key checks;
- type, null, domain, and range validation;
- documented outlier detection and disposition;
- clean execution of every affected notebook;
- successful Docker image build and applicable containerized checks;
- statistical support and wording review for every conclusion;
- updated README, notebook narrative, data dictionary, and decision records.

Validation failures MUST be visible and actionable; the pipeline MUST NOT silently continue after a
failed mandatory check. Exceptions require a linked issue, documented impact, and approval before
merge.

## Governance

This constitution supersedes incompatible plans, tasks, implementation preferences, and informal
decisions. Every specification, plan, task set, pull request, and level-completion review MUST include
a constitution-compliance check. Complexity and exceptions MUST be justified with evidence.

Amendments require:

1. an issue describing the proposed change and rationale;
2. an impact analysis covering principles, artifacts, and migration needs;
3. a pull request containing the amendment and required follow-up updates; and
4. explicit approval from the project owner.

Constitution versions follow semantic versioning. A MAJOR change removes or incompatibly redefines a
principle; a MINOR change adds a principle or materially expands governance; a PATCH change clarifies
wording without changing obligations. The amendment date MUST be updated whenever normative content
changes.

The project owner is the approval authority. Non-compliance with a mandatory principle or quality
gate blocks task, level, and project completion until corrected or formally amended through this
process.
